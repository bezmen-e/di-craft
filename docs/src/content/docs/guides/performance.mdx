## Recorded Result

In the public run recorded on **2026-11-11**, `di-craft` resolved a hot
singleton in a median **5.458 ns/op**. For that one scenario and the recorded
package versions, the participating containers measured **1.76× to 4.47×** its
median. These figures measure container overhead, not HTTP throughput or total
application performance. The
[raw result](https://github.com/bezmen-e/di-craft/blob/main/benchmarks/results/public-2026-11-11T14-57-42-521Z.json)
contains all fourteen rounds and the environment metadata.

A warm resolve reads one `Map` entry keyed by the token's `symbol` id and
returns the cached instance before any cycle or lifetime bookkeeping runs. The
benchmark scenarios cover these runtime choices:

| Runtime choice                | Effect                                                                                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Symbol-keyed tokens           | Registry and instance stores are `Map`s keyed by a unique `symbol` per token. Lookups compare by identity, with no string hashing or metadata tables.       |
| Explicit providers            | Registration is a flat `Map.set` with a duplicate check. There are no decorator side effects, constructor-name parsers, or reflection metadata to prepare.  |
| Cached singleton/scoped reads | A warm resolve returns from a single `Map.get` on the owning container's store before the resolution context is touched.                                    |
| Single parent-chain walk      | One loop finds both the provider and the container that owns it, so child-container lookups do not allocate or recurse per level.                           |
| Lazy shared context           | Cycle-path bookkeeping allocates one reusable context per resolver, on the first resolve that needs it.                                                     |
| Scope-aware host selection    | Singletons cache on the registering container, scoped services on the requesting child, and transient services nowhere, with no extra dispatch table.       |
| Async disposal                | Teardown snapshots and clears the store before running hooks in reverse creation order, so `dispose()` stays idempotent and re-entrancy safe.                |

## Benchmark Suite

The comparative workspace measures `di-craft` alongside InversifyJS v8.2.3,
Awilix v13.0.5 in PROXY and CLASSIC modes, TSyringe v4.10.0, TypeDI v0.10, and
Typed Inject v5.0.0, using Tinybench v2.9.0 on Bun v1.4.2. The `di-craft`
subject imports the production ESM artifact built from this repository. The raw
result records every package version and the machine environment used for the
run.

**Correctness before timing**

The adapter contract suite runs before Tinybench. Each adapter must provide the
same observable graph:

- `Logger`, `Config`, `Repo`, and `Service` act as root singletons
- transient graph nodes produce new instances per resolve
- each scope caches its own `ScopedService` while sharing the root logger
- deep and wide graphs wire the declared dependency counts
- each declared teardown API invokes the scoped service disposer

These checks keep lifetime or identity differences out of the timing
comparison. The timed scenarios measure cost only after the adapters pass the
contract against the production artifact.

**Measurement design**

The public runner performs a frozen-lockfile install, typechecks the benchmark
workspace, builds the production ESM package, and runs the contract suite
against that artifact. It then measures the subjects with these controls:

1. One balanced block contains fourteen rounds for the seven subjects. Across a
   block, each subject occupies each process position an equal number of times
   and follows each other subject an equal number of times.
2. Each subject runs in a fresh Bun process per round, so implementations do
   not share JIT feedback, inline caches, or GC history.
3. Tinybench warms each scenario for 50 ms and measures it for 100 ms. One
   sample executes a batch sized for that operation.
4. For each subject, scenario, and round, the runner divides the median
   Tinybench batch duration by the batch size and records normalized `ns/op`.
5. The reporter aggregates the fourteen per-round values with the median and
   the median absolute deviation (MAD).

Lower `ns/op` is better. MAD reports the spread around the median; it is not a
confidence interval. Process isolation and balanced launch order reduce
measurement bias, but they cannot remove OS scheduling, CPU frequency changes,
JIT decisions, or GC timing.

**Scenario boundaries**

Each scenario isolates one part of container work. Production code combines a
subset of these stages according to its lifetime model.

| Workload group          | Scenarios                                                         | Container work represented                                       |
| ----------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------- |
| Warm access             | Hot singleton resolve, warm scoped resolve                        | Cached service lookup in the root container or an existing scope |
| Object construction     | Transient resolve, deep graph, wide graphs (4 and 10 dependencies) | Cache misses, dependency traversal, argument assembly, and constructors |
| Startup and cold access | Registration, first resolve                                       | Graph configuration followed by initial cache population         |
| Scope lifecycle         | Scope creation, first scoped resolve, async teardown              | Per-request or per-job scope ownership from creation to cleanup  |

Tinybench setup hooks prepare cold graphs and scopes outside each timing
region. Cleanup for registration and resolve scenarios also stays outside the
timed operation. The teardown scenario times cleanup as its target operation.

TypeDI reports `N/A` for registration because its comparable service
definitions run as decorator side effects during module evaluation, which the
registration timer excludes. For async teardown, InversifyJS and TypeDI report
`N/A` because the suite found no equivalent public contract; Awilix (both
modes), TSyringe, and Typed Inject participate.

**Reading the result**

`di-craft` records the lowest median in 5 of the 11 scenarios: hot singleton
resolve, wide graph (4 dependencies), first resolve, scope creation, and async
teardown. It is within 3% of the lowest median in two more (transient resolve
and first scoped resolve) and second in five rows overall. The clearest gains
appear where the flat symbol-keyed registry, the single parent-chain walk, and
the small cache-miss path dominate the measured work: first resolve, scope
creation, and startup-adjacent operations.

`Warm scoped resolve` is the widest gap. Typed Inject records 1.708 ns because
it compiles an injector into direct closure calls; the row measures one cached
read from an existing scope and excludes scope creation, the first scoped cache
miss, and teardown, where the same production request pays separate costs
(rows where `di-craft` records the lowest median).

`Deep graph (10 levels)` and `Wide graph (10 dependencies)` remain behind
InversifyJS (1.28×) and Typed Inject (1.00×/1.13×). These rows measure full
cache-miss traversal: one resolve walks ten chained factories or assembles ten
dependencies, paying a registry lookup, a lifetime check, and an argument
object per level. `Registration` is third behind Typed Inject and TSyringe;
`di-craft` validates duplicates and lifetime capture on every register call.

**Match the scenario to the application**

The reporter does not compute an overall score because applications pay
different combinations of container work. A long-lived process may register
once and spend most of its time on warm singleton reads. An HTTP adapter may
create a scope, resolve one scoped graph, read cached scoped values, and
dispose the scope for each request. A worker may construct transient graphs
without opening scopes.

Do not average the relative factors across rows. The scenarios use different
batch sizes and isolate independent timing regions. Use the rows that match the
application's measured resolve pattern, then profile the full application with
its framework and I/O.

The comparison applies to the recorded package versions, adapters, fixtures,
and machine (Apple M5 Pro, Bun 1.4.2, macOS arm64). Each library keeps its
public lifecycle model, so `N/A` means the suite found no equivalent operation
for that row. The benchmark measures container overhead rather than end-to-end
request latency.

## Reproduce Locally

From the repository root:

```bash
bun run benchmarks:install
bun run benchmarks:precondition
bun run benchmarks:quick    # one short round, local iteration only
bun run benchmarks:public   # production artifact, 14 balanced rounds
```

The benchmark workspace is intentionally isolated from the root Bun workspace
and owns its comparison dependencies in `benchmarks/bun.lock`. Quick results
are for local iteration and must not be used for public claims; publishable
numbers come from `benchmarks:public` and are rendered with
`bun run benchmarks:report`. See the
[benchmark workspace README](https://github.com/bezmen-e/di-craft/blob/main/benchmarks/README.md)
for methodology, fairness notes, and fixture sources.
